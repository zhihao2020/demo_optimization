## 给 Agent 的修改任务

1. **先冻结算法，不进行任何“训练补救”。** 不修改 TD3 的 \(\gamma,\tau,\) actor/critic learning rate、网络宽度、reward 权重、exploration schedule、Gumbel 结构，不重新启用 GHTD3/SAC，不增加 storage-use reward，不把 deterministic GiveSafe 从 1 次改回 64 次，也不要通过开启 Shadow FMU 来掩盖一级 Oracle 的错误。正式 seasonal 主线目前明确 `enable_shadow=False`，保持这个设定。 当前任务是修复 safety/action interface，而不是调参。

2. **建立统一的动态动作“数值端点契约”，解决 `0.93000000715 > 0.9299999999999999`。** 当前 `HybridActor` 的动态 CAES 解码使用 Torch `float32`，然后在 `act_numpy()` 中转为 Python float；Oracle 区间来自 Python/NumPy double。 当前 `check_action_executable()` 对 CAES 动态区间使用 `1e-9`：

   ```python
   if not (lo - 1e-9 <= physical.u_caes <= hi + 1e-9):
   ```

   这与项目其他动作校验使用的 `_EPS=1e-6` 也不一致。
   在 `src/actions/caes_u.py` 新增统一常量，例如：

   ```python
   DYNAMIC_ENDPOINT_ATOL = 1.0e-7
   ```

   并新增纯数值函数：

   ```python
   def snap_to_interval_endpoint(
       value: float,
       low: float,
       high: float,
       *,
       atol: float = DYNAMIC_ENDPOINT_ATOL,
   ) -> tuple[float, bool]:
       lo, hi = min(float(low), float(high)), max(float(low), float(high))
       x = float(value)

       if lo <= x <= hi:
           return x, False

       if lo - atol <= x < lo:
           return lo, True

       if hi < x <= hi + atol:
           return hi, True

       return x, False
   ```

   注意这个函数**只能修正 ULP/float32 表示误差**，绝不能把一般越界动作投影回来。例如：

   ```text
   hi = 0.93
   0.930000007 → 0.93     合法数值 snap
   0.9301      → 0.9301   不允许 snap，后续必须拒绝
   ```

   这和原来的 `clamp_u_caes_to_spec()` 概念必须分开。不能把真正策略越界静默修正成可行动作。

3. **在 Actor 最终物理动作打包前执行一次 endpoint snap。** 修改 `src/training/hybrid_td3/actor.py::act_numpy()`。当前代码已经通过 `u_from_mode_onehot_dynamic()` 在动态区间上解码 CAES。 在得到：

   ```python
   u_caes = float(out["u_caes"][0].cpu())
   ```

   之后，根据实际选择的 mode 取：

   ```python

   feasible.u_caes_charge
   ```

   对该方向调用 `snap_to_interval_endpoint()`。idle 不处理。然后才进入 `physical_dict(...)`。同时增加诊断字段：

   ```python
   packed["caes_endpoint_snapped"] = bool(snapped)
   packed["caes_endpoint_snap_delta"] = float(snapped_value - original_value)
   ```

   这些字段仅用于 audit，不进入 FMU 控制三元组。

4. **Oracle 的动态区间比较必须使用同一个数值契约。** 修改 `src/actions/feasibility_oracle.py::check_action_executable()`，禁止继续硬编码 `1e-9`。将：

   ```python
   lo - 1e-9 <= u <= hi + 1e-9
   ```

   改成统一 helper/constant，例如：

   ```python

   ```

   或至少使用同一 `DYNAMIC_ENDPOINT_ATOL`。推荐调用同一个 helper，避免以后 Actor、Validator、Oracle 再产生三套 epsilon。真正超过 `atol` 的动作仍必须拒绝。

6. **为 CAES idle 建立独立的 robust one-step safety guard。** 当前 `_caes_mode_mask_base()` 的逻辑是：

   ```python

   ```

   即只要“现在”没越界就允许 idle。 但真实 FMU 已经证明 idle 一小时仍可能发生 pressure/SOC/temperature drift。因此新增：

   ```python
   def _caes_idle_step_ok(
       self,
       outputs: Mapping[str, float],
   ) -> tuple[bool, str | None]:
   ```

   这个函数**不依赖当前错误的 `predict_next_state(u_caes=0)`**，而直接利用 probe 标定的 idle residual + margin 构造 robust invariant envelope。

7. **idle guard 对 gas/hot/cold SOC 使用“双边距离”判据。** `feasibility_margins.yaml` 当前已有：

   ```yaml
   idle:
     residual_p99_gas: 0.02
     residual_p99_hot: 0.005
     residual_p99_cold: 0.01
     margin_gas: 0.01
     margin_hot: 0.01
     margin_cold: 0.01
   ```

   因为 idle drift 未区分正负方向，应该保守使用绝对残差：

   $$
   \delta_i^{idle}
   =
   r_{i,P99}^{idle}
   +
   m_i^{idle}
   $$

   然后要求：

   $$
   x_i-x_{i,min}>\delta_i^{idle}
   $$

   且

   $$
   x_{i,max}-x_i>\delta_i^{idle}.
   $$

   例如 gas SOC：

   ```python
   gas_guard = residual_p99_gas + margin_gas
   gas_ok = (
       gas >= gas_SOC_min + gas_guard
       and gas <= gas_SOC_max - gas_guard
   )
   ```

   hot/cold 同理。不要只保护下界。

8. **idle pressure 必须真正使用现有 65 kPa residual + 120 kPa margin。** 配置已有：

   ```yaml
   residual_p99_pressure: 6.5e4
   margin_pressure_Pa: 1.2e5
   ```

   定义：

   $$
   \delta_p^{idle}
   =
   65\,000+120\,000
   =
   185\,000\ {\rm Pa}.
   $$

   则：

   $$
   P_{\min}+\delta_p^{idle}
   \le P_t
   \le
   P_{\max}-\delta_p^{idle}.
   $$

   按当前 6.5 MPa 下界，压力约低于：

   $$

   $$

   时 idle 应被 mask。**6.685 MPa 不要硬编码**；代码必须从 `device_params + feasibility_margins` 计算。

### 两个修改背后的原理

**第一处是数值分析问题，不是约束放松。** Actor 内部采用 FP32，因此即使理论输出恰好为 \(0.93\)，实际可能存成：

$$
0.9300000071525574.
$$

而 Oracle 的 FP64 上界可能是：

$$
0.9299999999999999.
$$

两者物理上是同一个端点。正确做法是定义：

$$
|u-\bar u|\le\varepsilon_{\rm num}
$$

时把它视为同一个数值端点，而不是把真实可行集扩成：

$$
[\underline u,\bar u+\varepsilon].
$$

所以需要的是 **endpoint canonicalization**，不是安全 margin。

---

**第二处是 robust feasibility 问题。** 现在 Oracle 对 charge/discharge 已经有：

$$
x_{t+1}^{pred}
+
\text{residual margin}
\in\mathcal X
$$

的思想，但 idle 仍相当于假设：

$$
x_{t+1}=x_t.
$$

真实 FMU 已经证明：

$$
x_{t+1}
=
x_t+w_t^{idle},
\qquad
w_t^{idle}\ne0.
$$

因此如果已知 probe 给出了：

$$
|w_t^{idle}|\le \delta_{P99}+m,
$$

那么 robust idle admissibility 应要求：

$$
x_t\oplus[-\delta,\delta]
\subseteq\mathcal X.
$$

这就是为什么当前压力虽然：

$$
6.514\,{\rm MPa}>6.5\,{\rm MPa},
$$

仍不应该允许 idle：它没有足够的一步鲁棒裕量抵抗真实 FMU 的 idle 漂移。

---

这次修复完，论文里的第二个贡献“**state-dependent joint feasible support**”也会更扎实：不是仅仅约束 charge/discharge，而是让所有模式——包括看似“不动作”的 idle——都满足**一步鲁棒物理可行性**。同时 0.93 的问题必须被明确归为数值接口误差，不能拿它来扩大物理安全域。

**Agent 的最终完成条件只有一个：在不改变算法主结构和超参数的情况下，新 Oracle + endpoint contract 先让旧 checkpoint 完整、安全地跑过 168 h，再重新跑 30k Stage C；新 Stage C 的 C1–C5 全过之后，才允许 Stage D。**
