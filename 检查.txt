## 但我发现第一个需要继续修的地方：snap 的顺序还差一步

这是我认为**必须在正式 Stage D 前补掉**的小 P0。

当前 `FeasibilityOracle.check_action_executable()` 的顺序实际上是：

```python
physical = action

pred = self.predict_p_grid(outputs, physical)

# 先检查 grid
if pred > ...:
    reject

# 后面才根据 CAES interval 做 endpoint snap
u_checked, snapped = snap_to_interval_endpoint(...)
```

也就是说，**CAES 的 FP32 endpoint correction 发生在 grid constraint 检查之后**。

这留下一个很细的漏洞。

例如：

$$
u_C^{FP32}=0.93000000715
$$

理论端点：

$$
u_C^\star=0.93
$$

差：

$$
7.15\times10^{-9}.
$$

如果 CAES 额定功率约为 \(150\) MW，这个差异映射到联络线预测就是大约：

$$
150\times10^6
\times7.15\times10^{-9}
\approx1.07\text{ W}.
$$

而你当前 grid checker 恰好只有约 1 W 的数值 tolerance。

所以极端靠近联络线边界时仍可能出现：

> CAES interval 检查不会误拒了，但 **grid 检查先一步因为同一个 FP32 endpoint artifact 拒绝。**

正确顺序应该改成：

```text
raw physical action
        ↓
确定 CAES mode
        ↓
根据当前 feasible interval
执行 endpoint canonicalization
        ↓
canonical physical action
        ↓
predict_p_grid
        ↓
grid check
        ↓
next-state check
```

即在 `check_action_executable()` 开头就先生成：

```python
checked_physical
```

后面所有：

```python
predict_p_grid()
predict_next_state()
```

统一使用这个 canonicalized physical action。

这不是大改，但最好补掉，否则 numerical contract 还没有真正做到“单一入口”。

## 第二个我认为更值得修：`legalize_mode_mask()` 仍然会偷偷把空集变成全模式可行

现在 `caes_u.py` 还有这段：

```python
def legalize_mode_mask(mode_mask):
    ...
    fill = legal.any(dim=-1, keepdim=True)
    return torch.where(fill, legal, torch.ones_like(legal))
```

它的 docstring 甚至明确写着：

> `if a row is all-false, allow every mode.`

这和我们现在的安全语义是冲突的。

Oracle 现在已经专门支持：

```text
D=False
I=False
C=False
→ feasible_set_empty=True
```

而新测试也要求：

> 无合法 mode 时绝不重新打开 idle。

可神经网络内部的 utility 却还有：

```text
[False, False, False]
        ↓
[True, True, True]
```

正常 online 路径理论上应该在 actor 被调用前就捕获 `FeasibleSetEmpty`，所以它**未必是这次 Stage C 失败原因**。

但是现在 idle robust guard 加严之后，all-false state 出现概率会比以前更高。为了保持论文中：

$$
a_t\in\mathcal A_f(s_t)
$$

这个硬定义，我建议彻底取消这条 silent rescue。

至少改成：

```python
if not legal.any(dim=-1).all():
    raise EmptyModeMaskError(...)
```

在线控制路径：

> empty → `FeasibleSetEmpty`，不调用 actor。

对于 TD3 replay target，如果一个 next state 确实是 terminal/empty，可以用 `done=1` 避免 Bellman bootstrap，而不是把三个模式全部开放。

这个建议我认为很重要，因为否则你论文说：

> “no feasible mode is never silently reopened”

代码上还不是完全成立。

## 第三个小问题：`ENDPOINT_SNAP_HARD_FAIL` 目前实际上几乎触发不了

现在：

```python
DYNAMIC_ENDPOINT_ATOL = 1e-7
ENDPOINT_SNAP_HARD_FAIL = 1e-3
```

collector 只有当：

```python
caes_endpoint_snapped == True
```

时才检查 snap delta；但 helper 只有：

$$
|\Delta|\le10^{-7}
$$

才会设置 `snapped=True`。

因此正常代码下：

$$
|\Delta_{\text{snap}}|\le10^{-7}
$$

永远不可能：

$$
>10^{-3}.
$$

所以现在这个：

```python
if delta > ENDPOINT_SNAP_HARD_FAIL:
    raise RuntimeError(...)
```

更多是一个“理论保险丝”，而不是真正能发现 decoder 大越界的机制。

如果真想实现我们之前定义的审计逻辑，建议分别统计：

```text
raw_endpoint_miss_abs
numerical_snap_abs
```

如果 raw actor output 离所选 mode interval 超过例如 \(10^{-3}\)，直接报 decoder bug；只有 \(\le10^{-7}\) 才做 numerical snap。

这个不是安全阻塞项，可以排 P1。

## 实验流程目前还没有完全按要求完成

新提交自己也承认还没有做三件事：

1. 用旧 30k checkpoint 跑新的 **168 h greedy regression**；
2. 跑至少 **20,000 boundary stress actions**，要求 false-safe=0；
3. 新目录重新跑 Stage C 30k。

而当前 `pc_hybrid_queue.py` 实际流程仍是：

```text
Stage A
→ Stage B d53
→ Stage C d53ep
→ C通过才D
```

它没有把：

```text
old-checkpoint regression
boundary stress 20k
```

插到 Stage C 前面。

所以如果 agent 下一步准备直接运行这个 queue，我建议先补两个任务：

```text
Stage B
  ↓
Regression-R:
旧30k checkpoint + 新Oracle
168h deterministic TEST
  ↓
Stress-S:
20k boundary actions
false-safe=0
  ↓
Stage C d53 30k fresh
  ↓
C1-C5
  ↓
Stage D
```

这里 Regression-R 很有价值：它能直接回答：

> **修的是环境安全接口，还是必须重新学习策略？**

如果旧 checkpoint 换上 d5.3 后已经可以完整走 168 h，就证明我们对根因的定位很准确。

## 文档还有一处证据口径建议修正

新 `d5.3` 报告把 C3 失败写成：

> discharge、`mag=1`、`-0.32999998` 被投成 idle。

但你刚才给我的实际 Stage C `eval_failure.json` 口径是：

> charge \(u_{caes}=0.93000000715\)，上界 \(0.9299999999999999\)。

实际上这两个都是**同一类 FP32 endpoint bug**，而新增测试也确实同时覆盖了 charge 和 discharge。

因此报告最好不要把其中一个重新写成“唯一 C3 根因”，而应该改成：

> Two endpoint failures were reproduced: the charge-side upper endpoint and the discharge-side \(-0.33\) endpoint; both originate from float32 representation around dynamically decoded band boundaries.

同样，新报告中写“C2 的 6 次 false-safe”，而你这次 Stage C 总表是 **7/7**。这也应该统一，或者明确：

```text
7 total unsafe transitions
其中 6 条属于某 taxonomy
1 条属于 endpoint→idle / 其他类别
```

不要以后论文/工程报告里出现 6 和 7 两套数字。
